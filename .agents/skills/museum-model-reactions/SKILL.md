# 박물관 모델 맞춤 대사 제작

모델을 직접 관찰하고 설명에 근거해 성향별로 서로 다른 감상 대사를 작성한다. 담당자는 이 스킬을 실행하는 에이전트다. 이 스킬 자체는 업로드 감지기나 예약 실행기가 아니다.

## 1. 저장소와 실행 범위 확인

- 사용자 지정 저장소 또는 현재 작업폴더에서 `JohnLee305/myMusium`을 확인한다. 로컬 설치 사본에서 실행해도 실제 저장소 루트를 먼저 찾는다. 이 PC의 최근 작업 위치는 `C:\Dev\vr-museum-sync-20261016`이나 존재·origin·HEAD를 실제 확인한다. 클라우드에서 이 경로를 가정하지 않는다.
- 루트 `AGENTS.md`와 `docs/GIT_MULTI_AGENT_WORKFLOW.md`의 시작 Gate를 수행한다. 최신 `codex/museum-tycoon`·TASKS/PROJECT_STATUS/STATUS/WORKLOG/WORK_HANDOFF와 진행 PR을 확인한다. 기존 개인 자료/미커밋 작업을 보호한다.
- `docs/REACTIONS.md`, `docs/REACTION_CONTENT_SCALE.md` 및 실제 `apps/curator-admin/reactions.mjs`, `reaction-service.mjs`, Unity `ReactionCatalog.cs`의 현재 계약을 읽는다. 스킬에 기록된 한도보다 실제 최신 계약이 우선한다.
- 요청한 전시품 ID, 목표 개수, 작성만인지 작성·적용인지 기록한다. 사용자 지정 모델만 처리하며, 전체 미완성 모델 처리를 요청하면 manifest에 등록된 항목을 조사해 목록을 만든다. 파일 유무만으로 자동 템플릿을 맞춤 완료로 판단하지 않는다.
- 실제 Archive는 관리 `/api/health`의 archive와 관람 앱/바탕화면 바로가기 `-museum-archive`를 대조해 결정한다. 소스 작업폴더의 샘플 Archive를 개인 Archive로 오인하지 않는다. 활성 프로세스·포트를 재확인한다.

## 2. 관찰과 근거 기록

- 등록 metadata·설명과 PC 모델을 읽고 모델 SHA-256 및 제목/설명 sourceHash를 기록한다. 설명/모델을 대사 제작 때문에 수정하지 않는다.
- 기존 모델 미리보기로 최소 세 가지 의미 있는 각도(예: 앞/옆/뒤 또는 위)를 확인한다. 뒷면을 볼 수 없으면 관찰 범위와 미확인 부분을 기록한다. 보지 못한 특징을 만들어내지 않는다. 시각 도구가 없으면 관찰 단계 미완료로 남기고 설명 기반 초안과 구분한다.
- 색·윤곽·표면의 시각적 인상·부분 구성·대비를 추린다. 확인된 설명의 사실, 눈으로 관찰한 특징, 개인적 감상·가정 질문을 구분한다. 실제 재질 성분/제작자/시대/국가/제품명/용도·성능은 제공 근거 없이 단정하지 않는다.
- 개인 Archive의 `artifacts/{id}/reaction-observations.md`에 모델/설명 지문, 관찰 각도·특징·미확인 사항, 작성일·처리 주체, 작성/검토/적용 상태와 근거를 보관한다. 실제 모델/문구/관찰 이미지·메모는 공개 Git에 추가하지 않는다.
- 기존 관찰 메모와 모델 해시가 다르면 예전 승인 대사를 그대로 재사용하지 말고 재검토한다. 현행 런타임은 모델 바이트만 교체했을 때 자동 stale 처리가 없으므로 이 비교는 에이전트가 수행한다.

## 3. 맞춤 대사 작성과 품질 검사

- 기본 목표는 **40개 이상**, 일반·디테일·이야기·수집가별 최소10개다. 추가로 의미 있는 소재가 있으면96개(성향별24개)까지 작성한다. 사용자 지정 개수가 현재 한도를 넘으면 제한과 후속 구현을 설명하고 허위 완료하지 않는다.
- 일반: 첫인상·전체 윤곽·색 대비. 디테일: 구체적인 부분·표면·구성. 이야기: 설명의 실제 이야기나 관찰에서 떠오르는 열린 질문. 수집가: 전시 관점·비교하고 싶은 특징·컬렉션 관심. 모든 성향을 역사·가격 추측으로 채우지 않는다.
- 짧은 감탄, 보통 감상, 드문 코멘트를 섞는다. 같은 의미의 조사/어미/동의어 교체를 독립 대사로 세지 않는다. 말투는 자연스러운 관람객의 한국어 생각으로 쓴다.
- 기존 승인·수정·거절 내용을 먼저 읽고 보존한다. 기존 승인문이 충분하면 무조건 재생성하지 않는다. 남은 용량 안에서 보충하거나 변경이 필요한 항목을 명시해 수정한다. 검토하지 않은 기존 초안을 일괄 승인하지 않는다.
- 현재 v1 한도: 후보96개, 파일64KiB, 문구72 UTF-16 코드 유닛, 근거16개. 문구 ID의 유일성·성향/tier/status·금지 HTML/제어문자와 근거 참조를 실제 validator로 검사한다. persona는 4종 기본값 외 ID 형식의 새 값도 허용되며, 새 성향의 표시는 guest 성향 부여 후속이 필요하다. 원문 인용 evidence는 실제 원문 안에 있어야 한다. 시각 감상을 원문 인용이라고 꾸미지 않는다. 현재 시각 수동문은 `evidencePointIds: []`와 별도 관찰 메모로 기록할 수 있다.
- 문장별 근거·서로 다른 의미·모델에 맞는 내용인지 검토한다. 의미 중복 제거는 에이전트 검토이며 기계적인 문자열 중복 검사만으로 통과했다고 하지 않는다. 관찰 소재가 부족하면 수량을 부풀리지 말고 부족한 근거와 실제 개수를 기록한다.

## 4. 저장과 적용

- `작성/후보/검토용` 요청은 draft로 저장한다. `적용/사용하게/관람객에게 나오게` 요청은 해당 범위의 검토를 마친 새 대사를 approved로 저장하고 enabled를 확인한다. 기존 세션의 명시적 적용 권한을 다시 묻지 않는다. 이 스킬의 존재만으로 모든 미래 초안을 자동 승인할 권한이 생기는 것은 아니다.
- 관리 API를 사용한다: `GET /api/session`으로 토큰(출력/커밋 금지), `GET /api/reactions?artifactId={id}`로 document/revision/sourceHash를 읽는다. 기존 내용을 바탕으로 수정한 document를 `POST /api/reactions`에 `action: save`, artifactId/revision/sourceHash와 함께 JSON으로 보낸다. 헤더는 `Content-Type: application/json`, `X-Museum-Token`이다.
- API의 자동백업·원자적 저장·동시수정 방지를 사용한다.409이면 다시 읽고 차이를 비교하며 같은 payload를 무한 재시도하거나 타인의 변경을 덮어쓰지 않는다. 원문 stale면 새 원문 기준으로 검토한다. 손상 파일이면 백업/복구 경로를 확인하고 기존 자료를 조용히 교체하지 않는다.
- 적용 범위의 승인 개수와 성향별 개수, enabled/stale/error, 저장 후 문구 동일성·백업 존재를 재조회한다. metadata/모델/manifest/visitors가 의도치 않게 바뀌지 않았는지 해시로 확인한다. 열려 있는 관리 화면도 저장 내용을 다시 불러온다.
- 바탕화면 PC 관람이 최신 exe와 같은 Archive를 가리키는지 확인하고 필요하면 기존 setup 스크립트의 ArchivePath/Port로 연결한다. 기존 바로가기를 백업하고 재읽는다. 기준판/Quest 연결은 변경 요청 없이 바꾸지 않는다. 데이터만 저장했다면 불필요한 Unity 재빌드는 하지 않는다.

## 5. 실제 표시 검증과 인계

- 런타임은 감상 시작 시 파일을 읽고 해당 성향의 approved 문구를 선택한다. 적용 저장 후 다음 감상 또는 관람 앱 재실행으로 확인한다. 기본 문구가 나오면 잘못된 Archive/구버전 exe, 승인0개/특정 성향 누락, disabled/stale/파일 손상, 대상 전시품을 순서대로 확인한다.
- 말풍선은 실제 Viewing 상태, 반응 표시 켜짐, 가까운 전방7m, 최대2명·4.5초·반복 억제 조건을 가진다. 멀리서 말풍선이 없다는 이유로 대사 저장 실패로 단정하지 않는다.
- 도구가 가능하면 해당 전시품 감상 말풍선을 직접 확인해 저장된 맞춤 문구와 대조한다. API/파일 검증, 프로세스 경로·모델 로딩, 실제 말풍선 시각 검증을 각각 기록한다. 마지막 단계를 못 봤다면 **저장·활성화 확인 / 실제 표시 미확인**으로 보고한다. Quest는 실제 HMD로 확인했을 때만 검증 완료다.
- 작업 전후 STATUS/WORKLOG와 TASKS/PROJECT_STATUS에 대상 수·문구 수·검증 수준·미완료·다음 동작을 기록한다. 공개 기록은 일반화하며 개인 콘텐츠는 제외한다. 코드/공유 문서 변경은 작업 브랜치→PR→최신 베이스 확인→실험 브랜치 통합 절차를 따른다. 개인 대사 데이터만 처리했으면 실제 파일을 Git에 넣거나 형식적인 소스 변경을 만들지 않는다.
- 종료 보고는 `관찰 완료 → 초안 작성 → 품질 검토 → 승인·저장 → 실제 표시 확인` 중 어디까지 끝났는지 밝힌다.1,000개 저장/자동 시각 분석/업로드 후 무인 실행은 후속 기능이며 현재 지원으로 표시하지 않는다.
